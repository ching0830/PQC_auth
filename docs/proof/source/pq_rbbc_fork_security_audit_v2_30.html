2. Source-framework alignment

The authoritative revision defines a three-pass blind-signature framework. In Protocols 3 and 4, the user commits to r, computes h = H(mu,c_r) and y = F(r)+h, and sends (y,pi_1) to the signer. The final signature is (c_r,c_x,pi_2). For Blind-UOV with the identity masking map, Section 5.3 specializes the equation to Q(x)=r+h. The paper's Blind-UOV-III row uses a 576-bit mask and a 1,472-bit UOV preimage.

3. Reduction dependency audit

3.1 Source one-more chain

The paper's Theorem 1 reduces the unblinded EUF-CMA+ game to the underlying hash-and-sign EUF-CMA game plus CAP extraction failure:

Adv_USIG(A) <= Adv_HS-SIG(B) + Adv_KS-CAP(C).

The reduction must extract r from c_r using the CAP oracle query/response list before programming the message hash. Paper Definition 10 requires extraction from the commitment and oracle transcript, without the proof as extractor input.

The paper's Theorem 2 then extracts (mu,r,rho) from the request proof and reduces one-more unforgeability to EUF-CMA+ plus NIZK extraction:

Adv_BSIG(A) <= Adv_USIG(B) + Adv_KS-NIZK(C).

The source explicitly separates the two random-oracle stages. A fork proof must preserve that separation; a single informal “all hashes are random” step is not an adequate substitute.

3.2 Source blindness chain

The paper's Theorem 3 uses NIZK zero knowledge, CAP zero knowledge, and pseudorandomness of the masking map:

Adv_BLIND(A) <= Adv_ZK-NIZK(B) + Adv_ZK-CAP(C) + Adv_PRG(D).

For the identity masking map, the fork still must establish uniform and independent sampling of the 576-bit r in the real protocol. A deterministic replay seed is only an evidence fixture and cannot be used as protocol randomness evidence.

3.3 PQ-RBBC cross-message binding

The repository proof defines J_m(r,rho)=r+H_RBBC(m,CAP.Commit(r;rho)) and gives the conditional ideal-QROM bound:

Adv_xmsg <= Adv_CAP-unique + Adv_CAP-extract + O(q_H^3 / 2^576).

The v2.29 replay closes the exact serialization and parent wire join needed to state this game. The bound nevertheless remains conditional because the two CAP terms have not been discharged and the concrete Anemoi construction has not been justified as the independent quantum random oracle assumed by the theorem.

5. Negative result and safe claim boundary

The bounded audit finds no basis for promoting fork_security_proof_revalidated. In particular:

  1. the paper proves the framework under explicit CAP, NIZK, random-oracle, masking, and underlying signature assumptions;
  2. the fork has exact functional row evidence but not proofs of those cryptographic properties;
  3. the available native module explicitly describes itself as an import contract and not a TCitH implementation;
  4. the test adapter is not a native Blind-UOV implementation;
  5. paper signature sizes are comparison targets and have not been measured for the fork.

The safe output is therefore a closed internal audit checkpoint with independent_review_ready=true, while CAP review, blindness, one-more unforgeability, full fork-security revalidation, backend qualification, size benchmarking, and production closure all remain false.

6. Independent-review checklist

An independent reviewer should reject the packet unless every item below is supported by a digest-bound artifact or is retained as an explicit assumption:

  1. Verify all source and generated artifact byte lengths and SHA-256 values.
  2. Confirm that the source revision is the 2025-10-31 revision of ePrint 2025/895.
  3. Check that the signing request is (y,pi_issue), where y is the only serialized request data field and pi_issue replaces only source pi_1.
  4. Audit CAP unique-witness and straight-line extraction in the exact fork oracle model; functional mutation tests are insufficient.
  5. Audit the two-stage source one-more reduction and every extractor, oracle-programming, abort, and advantage-loss step.
  6. Audit blindness with real fork randomness and both proof simulators.
  7. Audit QROM domain separation, query counting, and the boundary between the ideal oracle theorem and concrete Anemoi.
  8. Confirm that v2.29 semantics—not a sibling tree transcript or observed stream-byte estimate—are used.
  9. Do not approve paper size or interoperability claims without fresh fork measurements and vectors.
