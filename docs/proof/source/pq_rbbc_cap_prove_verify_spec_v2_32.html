Status: implementation input and gap record; not an accepting production proof specification. Relation: 589,030,555 rows, zero verification failures and zero external assertions under the frozen v2.29 identity. No row replay or proof generation is performed by this artifact.

1. Sources and interpretation boundary

The normative algorithm family is the TCitH CAP of ePrint 2025/895, Definition 8 and Protocols 10–11 (revision dated 2025-10-31). Its optimized opening and proof-of-work are described by ePrint 2024/490, Sections 3.1 and 4, and summarized by ePrint 2024/541, Section 5.3. The selected paper profile is NIST III / Shorter / TCitH: 18 repetitions, two vectors of 212 leaves, sixteen vectors of 211 leaves, Topen=174, explicit w=9, reported total work 13.9 bits.

The fork uses Anemoi-193/336 and is expressly not bit-exact Blind-UOV. Paper security statements do not transfer automatically. In particular, the paper's optimized construction uses one interleaved GGM tree for the 18 vector commitments, whereas the current forked CAP.Commit materializes 18 independent roots. This difference is security- and serialization-relevant.

3. Required CAP.Prove semantics

The future production prover must implement all steps below. A function that only serializes the envelope is not CAP.Prove.

  1. Strictly decode the public statement; derive the relation polynomials from the frozen relation/profile rather than accepting them from the witness.
  2. Parse the CAP state and c_r. Append the 1,472-bit signature witness x as the raw delta c_x. Concatenate both witness deltas and pad only as prescribed by Protocol 11.
  3. Compute the post-append h2 from the pre-append consistency digest carried by c_r, the deltas, the exact public statement, and a new fork-specific domain. The current source name h2 corresponds to the paper's pre-append h2'; the implementation must not alias these two transcript values.
  4. Derive every gamma[k,j] for k=1..rho and every relation polynomial. Compute the corrected witness polynomials for all 18 repetitions.
  5. For each repetition and k=1..rho, compute Q[e,k](X)=q[e,k]+X*Qbar[e,k](X) satisfying the degree-2 relation identity of Protocol 11. The complete 589,030,555-row relation is the only admissible production relation.
  6. Starting with counter zero, derive h3 from the statement, h2, all q/Qbar values, and the canonical counter. Decode hidden indices using the exact mixed-tree injective mapping. Require the explicit 9 challenge bits to be zero and require that the interleaved unified-tree opening contains at most 174 revealed nodes. Increment the counter and retry otherwise.
  7. Serialize pi_2=(h3, opening, {Qbar[e,k]}) canonically and return the complete proof envelope. Fresh cryptographic randomness is mandatory.

4. Required CAP.Verify semantics

  1. Strictly decode the statement and the complete proof. Reject wrong magic, version, profile, order, duplication, unknown sections, length overflow, non-canonical field elements, truncated data, or trailing bytes before algebraic verification.
  2. Parse c_r, raw c_x, counter, h3, the unified-tree opening, and every Qbar[e,k]. Recompute the exact Fiat–Shamir transcript including the statement and counter.
  3. Require the explicit 9 challenge bits to be zero. Decode all 18 hidden indices, reconstruct the interleaved unified-tree frontier, require at most 174 nodes, and verify its root and hidden-leaf commitments.
  4. Reconstruct corrected evaluations vP'' and vM at each hidden point. Re-derive every gamma. For all 18 repetitions and all rho=16 combinations, reconstruct q[e,k] from the Protocol-11 evaluation equation and check the recomputed h3.
  5. Accept only if every structural, PoW, opening, transcript, and degree-2 relation check succeeds. The verifier receives neither witness, prover randomness, nor an oracle transcript supplied by the prover.

6. Security and claim boundary

The current mixed-tree degree term is 2−182 before PoW at one oracle query. Adding 13.9 to 182 is not a complete ROM or QROM proof. Required accounting includes degree acceptance, hidden-leaf probability, oracle collision/guessing, universal-hash consistency, constraint sampling, grinding, multi-target/adaptive-session loss, the concrete Anemoi idealization, and QROM measurement/programming.

No accepting proof exists in this checkpoint. CAP.Prove, CAP.Verify, fork PoW, production proof serialization, CAP security qualification, fork-security revalidation, and production closure all remain false. System architecture, ticket lifecycle, and pq_sat_auth are unchanged.
