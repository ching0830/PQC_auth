# 第一堂：這篇論文要解決什麼問題？

日期：2026-09-12。所屬：[學習路線](../ROADMAP_zh-TW.md) 階段 1。
起點：會基礎 Python；本堂不要求密碼學或工程背景。
本堂完成條件：能用自己的話說明使用情境、認證需求、隱私問題與受控追責。

我們先建立研究問題，讓後面每個角色、公式與程式都有明確用途。
本堂的連線例子是教學情境；對完整系統的描述是研究設計目標，完成狀態由正式研究文件界定。

## 從一位使用者開始

假設你在偏遠地區工作，需要透過衛星網路把資料傳回研究室。你已向服務提供者註冊，
並取得使用資格。裝置準備開始使用服務時，會發出一個接入請求。

「接入」就是申請開始使用網路服務。能傳送一段無線訊號，還不足以讓系統決定提供服務。
為了說明本專案的分工，先把路徑畫成：

```text
你的裝置 ⇄ 衛星中繼路徑 ⇄ 負責檢查接入的地面站
```

「中繼」表示幫忙轉送訊息。這張圖只顯示資料路徑；發行與開啟身分等角色稍後再加入。
本專案把主要接入驗證與連線端點放在地面站，衛星可中繼或執行指定的輕量檢查。

## 為什麼需要認證與授權

服務提供者需要判斷：這個請求是否具有有效資格，以及送出請求的人是否真的能證明
相應的憑證持有關係。否則，單憑「我是合法使用者」的聲明，就可能讓其他人冒用資格。

本堂先區分兩個詞：

| 概念 | 要回答的問題 | 情境例子 |
| --- | --- | --- |
| 認證（authentication） | 對方能否證明所宣稱的身分或憑證持有關係？ | 不是只有知道別人的帳號或複製一段資料 |
| 授權（authorization） | 根據規則，允許對方使用哪些服務？ | 資格是否仍有效，是否適用於這個服務範圍 |

認證與授權需要配合。確認某人持有憑證之後，還要確認那份資格在此時此地適用。
我們希望驗證者得到足以做出這些判斷的證據。

## 每次交出固定身分，會多暴露什麼？

先考慮一個簡化設計：每次接入，都讓驗證端收到並記錄同一個固定帳號。

```text
帳號 U：星期一，服務範圍 A，接入
帳號 U：星期二，服務範圍 B，接入
帳號 U：星期三，服務範圍 A，接入
```

接收這個帳號的驗證端就能把三筆紀錄串在一起，可能由時間與服務範圍推測使用模式。
即使把傳輸內容加密，收到並能讀取帳號的一方仍然知道帳號；傳輸保護與向接收者隱藏身分
是不同的設計需求。本例不假設路上的每一個旁觀者都能看見加密內容。

把帳號改成固定假名 `X7`，仍能形成三筆 `X7` 的紀錄。這叫「可連結性」：
觀察者可能不知道姓名，卻知道不同次使用來自同一識別值。

因此，本研究除了不直接暴露註冊身分，也關心不同次使用能否被連結。
能隱藏到什麼程度，仍受到時間、可見設定等資訊與信任假設限制。

## 本研究希望分開兩件事

在預定設計中，註冊／發行端會驗證你的註冊身分，之後提供供接入使用的票券。
接入端驗證票券、持票者與使用條件，而不直接取得你的註冊身分。

```text
事先取得資格：使用者 ⇄ 發行端（在這裡完成註冊身分驗證）
                         ↓ 取得票券
後續接入服務：使用者 ⇄ 衛星路徑 ⇄ 地面驗證端
                         出示票券與此次接入所需證據
```

「票券」先理解為一份可供驗證資格的數位資料。它會出現在後續的程式與公式中。
要做到保護隱私，還必須防止發行端利用發行紀錄，直接認出日後出示的票券；
後面的盲簽章課程會解釋這個需求。

數位票券可以被複製，所以安全接入不能只靠「對方拿出一串 ticket bytes」。
持票者驗證、使用次數與重送處理都有自己的課程，本堂先理解它們需要存在的原因。

## 為什麼還要保留受控追責？

假設系統收到與某次使用有關的濫用證據，治理規則要求調查。研究目標是在一般接入時保護
註冊身分，同時保留一條受授權控制的身分開啟流程。

預定流程要求授權綁定案件、用途等條件，並需要足夠的開啟權責成員提供有效份額。
「門檻」就是完成操作所需的最少有效參與數；實際數量由系統設定。

這樣安排的理由，是限制單一接入驗證者或單一權責成員自行開啟身分的能力。
代價是需要額外治理、協調與稽核，也必須面對成員串通或不可用等情況。
本專案分離發行治理與身分開啟的金鑰與權限；具體角色與安全條件會在後續課程介紹。

這裡還要區分「介面拒絕未授權請求」與「能抵抗多少成員共謀」。以假設的 3-of-5 為例：
正常的開啟介面必須拒絕缺少有效授權的請求，即使有三個成員願意合作也一樣。
但若攻擊者已掌握三份秘密金鑰份額，能繞過該介面自行計算，不能只靠程式中的授權檢查
宣稱仍可阻止開啟。三位成員願意透過介面合作，與三份秘密金鑰已被攻擊者控制，並非同一情境。

本專案的 [核心 proof 定義](../../docs/proof/source/pq_rbbc_sgtd_core_proof_v1.tex)
在開啟隱私模型中限制攻擊者取得的秘密份額少於門檻。這是「信任假設」：安全結論需要成立的
前提。達到門檻的秘密份額被控制時，已超出這項模型的保護範圍；不能宣稱能阻止任意規模的共謀。
而 [opening checkpoint](../../docs/artifacts/CONDITIONAL_OPENING_GATE_v0_1_zh-TW.md)
目前提供的是具拒絕檢查的控制流程，production 門檻密碼學仍未完成。

開啟得到註冊身分也不能單獨證明某人確實做過被指控的行為；仍需正確綁定票券、事件證據，
並分析防止誣陷的條件。這也是論文必須處理的追責邊界。

## 為什麼衛星情境會影響設計？

本專案的架構把衛星節點視為資源受限，而且不預設可信。因而希望把高成本的發行與開啟
工作放在地面端，讓經過衛星的接入訊息與計算保持精簡。

本專案所說的「離線發行」是把發行與當次衛星在線接入分開：使用者事先取得資格。
它不表示發行端完全不需要網路，也不表示接入地面站完全不需要狀態或其他支援。

這項選擇需要評估使用者預先取得票券的成本、地面端依賴，以及當下連線的通訊與計算成本。
目前不能只從流程圖就宣稱已經比其他設計快；效能需要實驗。

「後量子」先理解為密碼學設計以抵抗具有量子計算能力的攻擊者為目標。
它不表示使用量子通訊。後續會說明各項密碼學工具，以及整套設計需要哪些安全假設。

## 本堂如何連到你的論文

| 本堂提出的需求 | 後續會遇到的設計 |
| --- | --- |
| 有效資格才能接入 | 發行授權、票券驗證、持票者認證 |
| 接入時保護註冊身分，限制紀錄連結 | 盲發行、共同設定與隱私分析 |
| 符合授權條件時可追責 | 票券內的追責資料、開啟授權與門檻開啟 |
| 控制衛星路徑的負擔 | 離線發行、地面驗證與分開的效能量測 |
| 能安全建立及延續連線 | 認證式金鑰建立、使用狀態、撤銷與換手 |

這些是要互相配合的研究目標。依教材基線的
[研究狀態](../../RESEARCH_STATUS_zh-TW.md)，完整持票者認證、衛星 AKE、可持久保存且
跨地面站一致的使用紀錄、production opening 與端到端評估仍未完成。
我們學的是目前設計與實作，以及它們尚未填補的缺口。

可以先參考這段研究問題的示範說法，再嘗試用自己的話表達：

> 我研究衛星網路接入時，如何驗證使用資格，同時減少註冊身分與使用紀錄的暴露。
> 設計還希望在符合明確授權條件時提供追責能力，並考慮衛星路徑的成本與後量子安全。

這段是教學示範，不是學習者已完成的答案或論文成果宣告。

## 理解檢查

先回答第一題，再依對話逐步處理其餘題目。答案重點是理由，可以直接用日常語言。

1. 一位已註冊的使用者接入服務時，驗證端需要確認什麼？是否必須每次取得其註冊身分？
2. 每次使用同一個假名，能否避免不同連線被串起來？
3. 為什麼身分開啟需要明確授權與多人共同控制？
4. 用 2–3 句話說明這篇論文的研究問題。
