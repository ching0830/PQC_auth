# 第十堂：一次發行中的公開輸入、秘密與 NIZK

日期：2026-09-14。所屬階段：3／完整系統流程。
接續 [第九堂](09_CONFIGURATION_AND_ISSUER_AUTH_zh-TW.md)。沿用小明的申請，將第四堂
的盲發行概念拆成輸入、輸出與資料可見性；目前不要求讀懂底層多項式或電路。

## 本堂的位置與前提

共同設定已核驗、HNCC 有適用的發行授權，接著才處理小明這次申請。
本堂要解釋：HNCC 不取得完整票券時，如何要求它綁定正確身分、持票者秘密及此次請求。
以下是正式核心所定義的流程，不表示目前已有可直接執行的完整發行服務。

## 1. 確認這次申請的身分與識別值

HNCC 透過註冊認證程序，確認小明這次申請對應的註冊身分 `rid`，並指定新的發行
session 識別值 `sid`。身分驗證的方法尚未由這堂課選定，`rid` 也不是使用者隨意填寫
便可信的欄位。其正式數位表示與註冊資料的對應需由註冊流程管理。

`sid` 辨認一次發行流程；`sn` 辨認一張票券。HNCC 需要前者管理這次申請，
後者在發行時是隱藏票券內容，日後出示票券才讓 FGS 看見。它們不能互相取代。

這裡的隱私目標是：HNCC 雖知道「小明曾申請」，仍無法在指定安全假設內，從發行紀錄
辨認日後哪張票券出自這次申請。並不是對 HNCC 隱藏註冊認證當下的身分。

## 2. 小明的裝置在本機建立票券內容

裝置使用已認證設定，產生本張票券的新秘密、序號及規定格式的加密隨機資料。
票券內容 `M` 有四個概念欄位：

| 欄位 | 用途 | 發行時的可見性 |
| --- | --- | --- |
| `ctx` | 綁定共同設定 | HNCC 已知；隱藏票券內也必須與它相符 |
| `sn` | 本張票券的序號 | 留在隱藏票券中，不直接交給 HNCC |
| `h` | 由本張票券的持票者秘密算出的摘要 | 留在隱藏票券中；秘密本身另留在裝置 |
| `C` | 綁定 `rid` 與同一個 `sn` 的追責密文 | 留在隱藏票券中；明文不包含持票者秘密 |

裝置再依固定編碼計算整份 `M` 的摘要 `m`。大小寫有意義：`M` 是內容，`m` 是
其摘要；`h` 只綁定持票者秘密，與 `m` 的用途不同。

接著用盲簽章方案規定的隨機資料，建立盲化請求 `β`；核心構造也把它記作 `y`。
盲化不是只把 `M` 做一次雜湊就送出：依本方案還要完成 CAP 與請求的綁定計算，
並保留完成簽章所需的資料。本堂先掌握用途，計算細節留待實作單元。

## 3. 產生並傳送發行 NIZK

裝置使用公開輸入 `x` 與秘密見證 `w` 產生 `pi_issue`，HNCC 用 `x` 與 `pi_issue`
驗證。此處「公開」只表示這次證明的驗證者 HNCC 可以取得，不代表對全網公告，
也不代表日後 FGS 會拿到相同資料。

依核心正式定義，`x` 包含共同公開參數、`ctx`、`sid`、已認證的 `rid` 與 `β`。
其中一部分先前已約定或由 HNCC 持有，不表示每一項都必須在同一封網路訊息重傳。
`w` 包含隱藏票券 `M`、持票者秘密、追責加密隨機資料及盲化所需秘密資料。

HNCC 要驗證的 I1–I5，可依用途讀成：

1. 隱藏的 `M` 符合票券格式，而且使用這次指定的 `ctx`。
2. `m` 確實由這份 `M` 的固定編碼算出。
3. 收到的 `β` 確實對應這個 `m` 及規定的盲化關係。
4. `M` 中的 `h` 確實由證明者掌握的持票者秘密算出。
5. `M` 中的 `C` 依規定加密這次已認證的 `rid` 與同一張票券的 `sn`，
   並與 context、持票者摘要等必要資料綁定。

這些條件要在**同一個發行關係**中成立。舉例：小華以自己的註冊身分申請，卻把小明的
身分加密進票券，企圖日後讓小明被追責。只有「密文格式正確」不足以阻止他；I5 還要求
密文內身分與 HNCC 這次認證的小華一致。若小華拿一份合規票券的證明搭配另一個請求，
I2–I3 的綁定也必須讓原證明無法直接沿用。這是設計要求的情境說明，並非本堂新跑的測試。

`pi_issue` 是一份強化後的發行關係證明，保留原請求合法性的規則，再加上票券、秘密與
身分綁定；不要畫成另附第二份相同用途的請求證明。NIZK 不需驗證者即時出題，
但整個發行仍需註冊認證、申請與簽署回應，不能因此說完整發行完全沒有往返。

## 4. HNCC 回應，裝置完成票券

HNCC 檢查身分、期間、額度、發行重放狀態與 `pi_issue`。通過後才執行
`BlindUOV.Respond`，將簽署回應 `z` 交給裝置。第九堂的管理函式不會自行完成這些全部工作。

裝置以 `z` 及本機保留的資料執行 `BlindUOV.Finalize`，得到最終簽章 `sigma`，
並以發行者公鑰核驗後，保存可使用票券 `T = (M, sigma)`；持票者秘密分開保護。
`z` 是給裝置完成簽章的回應，不能直接當成最終 `sigma`。

日後出示 `T` 時，不把 `β`、`pi_issue`、`rid` 或 `sid` 作為額外明文欄位一起傳給 FGS。
FGS 能看到 `M` 的序號、摘要與追責密文，卻不因此取得註冊身分明文。
`pi_issue` 與最終簽章可能包含的底層證明不同；不能推論接入完全沒有證明計算。

## 現有程式如何對應，哪些地方不能照名稱推論

| 程式入口 | 可以從中學到什麼 | 本堂保留的界線 |
| --- | --- | --- |
| [pq_rbbc_reference.py](../../src/pq_rbbc_reference.py) 的 `TicketPayload`、`build_honest_instance()` | 欄位表示、摘要、追責資料與請求如何在本機組成一組資料 | 使用測試 adapter 的 reference 範例，不是真實發行服務 |
| 同檔的 `IssueStatement`、`IssueWitness`、`verify_relation()` | 分別整理資料，再直接代入秘密檢查綁定規則 | `verify_relation()` 接收 witness，回傳規則檢查結果；不是 NIZK verifier |
| [pq_rbbc_blind_uov_abi.py](../../src/pq_rbbc_blind_uov_abi.py) 的 `BlindUOVRequest` | 對外盲化請求的 `masked_target` 表示與編碼 | 不含 `pi_issue`；本機 adapter 的 `verify()` 也不可冒充完整 NIZK 驗證 |
| [既有 reference tests](../../tests/test_pq_rbbc_reference.py) | 固定資料及變造案例如何檢查關係 | 關係測試不等於合格證明系統或不可連結性證明 |

特別注意：reference 的 `IssueStatement` 含有完整 `payload`，`generate_issue_circuit()`
也將其欄位列為該增量電路的公開輸入；這個物件沒有完整協定的 `sid` 欄位。
**這不是正式發行 NIZK 的完整公開輸入配置。** 不可把它直接序列化當成要傳給 HNCC 的
訊息，否則會暴露本來應隱藏的票券。正式核心中 `M` 位於秘密見證 `w`；實作整合必須
維持這個邊界。此處記錄已核對到的表示差別，不修改既有 producer 或宣稱已完成修正。

目前已有可執行關係與大量電路工程，合格的後量子 NIZK 後端、完整盲簽署及發行整合
仍有缺口。不可連結性仍依誠實執行但好奇的 HNCC、共用 metadata、誠實持票者及
開啟端被控制份額少於門檻等假設；這堂資料流不提供流量／時間側資訊的保證。
