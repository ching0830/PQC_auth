# 第三堂：簽署金鑰、驗證金鑰與票券簽章

建立日期：2026-09-14。所屬：[學習路線](../ROADMAP_zh-TW.md) 階段 2，必要安全概念。
接續：[第二堂](02_TICKET_AND_HOLDER_AUTH_zh-TW.md) 的票券驗證與持票者認證分工。
本堂先完整示範，不要求先答完第二堂問題；理解狀態以後續應用記錄。

## 本堂用途

理解地面站如何檢查票券簽章，以及為什麼可以給它驗證能力而不給它發行端的簽署能力。
先說明金鑰的責任，再對照核心論文中的 `VerifyTicket` 定義。
以下是既有設計及其概念說明，不宣稱完整簽章與接入實作已完成。

## 兩種不同的金鑰

金鑰先理解成密碼學運算需要的一份資料。簽章系統的金鑰產生程序會產生配對的
簽署金鑰與驗證金鑰，兩者的用途不同。

| 金鑰 | 誰持有／使用 | 用途 |
| --- | --- | --- |
| 簽署金鑰，也稱私鑰 | 發行端保密保存 | 支持產生符合該發行端驗證金鑰的簽章；在本專案中用於盲發行回應 |
| 驗證金鑰，也稱公鑰 | 可供使用者與地面站取得 | 配合票券內容與簽章，驗證三者是否符合指定驗證規則 |

簽章的安全要求是：公開驗證金鑰不應提供偽造未獲授權簽章的能力。地面站因而可以驗票，
而不持有發行端私鑰。驗證公鑰仍須來自可信的系統設定；不能直接相信任意提交者附上的公鑰。

發行端的簽署私鑰與使用者的 holder secret 是不同資料。前者參與發行簽章，後者支持
使用者接入時的持票者認證；不要因為兩者都必須保密，就把它們當成同一把金鑰。

## 沿用小明的完整例子

1. 小明依正式流程取得一張票券。票券可先看成「票券內容，加上一份對應簽章」。
2. 小明向地面站出示票券。地面站已有可信的發行端驗證公鑰。
3. 地面站按規定解讀票券內容、重算內容摘要，再使用公鑰檢查摘要與簽章。
4. 簽章驗證失敗就拒絕；通過表示完成這一項檢查，接入仍需其他條件。

若小華改動票券內與持票者秘密綁定的值，再沿用原簽章，票券內容就已改變。
安全的摘要及簽章設計要求這種未獲授權的改動不能靠原簽章通過。
簽章不是和內容無關、可貼到任何票券上的固定標記。

簽章驗證也不是把票券解密：本堂談的是驗證內容與簽章的關係。
內容保密及追責資料的開啟使用另外的機制；公鑰驗票不會自動給地面站身分開啟權限。

## 對照核心 `VerifyTicket` 定義

在核心論文中，票券寫成 `T = (M, sigma)`：

- `M` 是票券內容。
- `sigma` 是票券簽章。
- `bvk` 是發行端的驗證公鑰；對應的簽署私鑰叫 `bsk`。

核心先按規定編碼內容並計算摘要，再執行 `BlindUOV.Vfy(bvk, m, sigma)`。
下列 Python 寫法只說明簽章驗證這一步的資料流，函式名稱是教學佔位符，不可直接執行：

```python
ticket_bytes = encode(ticket_contents)
ticket_digest = hash_ticket(ticket_bytes)
valid = verify_signature(issuer_public_key, ticket_digest, signature)
```

`encode` 依約定把內容轉成 bytes；`hash_ticket` 計算票券內容摘要；`verify_signature`
拿公鑰、摘要與簽章，回傳驗證結果。這段省略了完整 `VerifyTicket` 的格式／共同資訊政策
檢查，也不包含持票者認證、票券消耗或整個接入協定。

## 本專案的盲簽章邊界

本專案使用盲發行。使用者準備隱藏內容的請求；發行端完成規定檢查後，以簽署私鑰產生回應，
再由使用者完成最終票券簽章。不能把它畫成「小明把完整票券明文交給發行端直接簽名」。
本堂只取簽署／驗證金鑰的分工及最終驗票流程；後續再完整示範盲簽章與發行 NIZK 的合作。
